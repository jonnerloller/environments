# Telegram reminder env

This folder holds the local-only pieces for Jonathan's Telegram reminders.

## Architecture (current)

```
Bitwarden (telegram_clawphi)
        │
        ▼  scripts/apprise/refresh_configs.sh
   Apprise (apprise.services.phitrine.com / "telegram" key)
        │
        ▼  HTTP POST /notify/telegram
   send_telegram_message.sh  ──►  Telegram Bot API  ──►  your phone
```

- **Bitwarden** is the source of truth for the bot token + chat id (item `telegram_clawphi`, custom fields `token` / `chat_id`).
- **Apprise** is the central notification gateway; the bot token only ever lives in Bitwarden + Apprise's config dir.
- **`send_telegram_message.sh`** (in `scripts/telegram/`) is a thin wrapper that POSTs to Apprise. No bot token in env required.

## Files

- `telegram.env.example` — historical template (kept for reference)
- `telegram.env` — *legacy* local cache, generated by `refresh_env.sh`; **no longer required** by the sender script. Some old consumers may still source it.
- `refresh_env.sh` — pulls token + chat_id from Bitwarden and writes `telegram.env`. Useful if you have a legacy consumer; otherwise unnecessary.
- `install.sh` — symlinks systemd user units and enables timers
- `systemd/` — user timer/service units (exercise + daily journal reminders)

## First-time setup on a new machine

1. Make sure the Bitwarden agent is set up — `~/.config/bw/agent.env` should exist (chmod 600) with `BW_CLIENTID`, `BW_CLIENTSECRET`, `BW_PASSWORD`, and `NODE_EXTRA_CA_CERTS` (Caddy root) populated.
2. *Only if Apprise is being deployed on this machine for the first time:* run `~/repo/environments/scripts/apprise/refresh_configs.sh` to populate Apprise's `telegram` key from Bitwarden.
3. Run `./install.sh` here — symlinks and enables the user timers.

## After rotating the bot token in Vaultwarden

1. Update the `token` field on the `telegram_clawphi` item.
2. Run `~/repo/environments/scripts/apprise/refresh_configs.sh`.
3. Also run `~/repo/environments/scripts/openclaw/refresh_secrets.sh` (openclaw is a separate consumer and hot-reloads).
4. (Legacy / optional) `./refresh_env.sh` here, if any consumer still reads `telegram.env`.

## Sending a message (any agent, any script)

```bash
"$HOME/repo/environments/scripts/telegram/send_telegram_message.sh" --message "hello"
```

That's it. No env file to source. The script POSTs to `https://apprise.services.phitrine.com/notify/telegram` and trusts Caddy's internal CA from `~/docker/caddy/caddy-root.crt` automatically when present.

For consumers on other machines, override:

- `APPRISE_BASE_URL` — if Apprise lives elsewhere
- `APPRISE_KEY` — to send through a different channel (`discord`, `email`, etc., once configured)
- `CADDY_CA_CERT` — path to the Caddy root cert if not at the default location

## Bitwarden CLI reference (for agents and ad-hoc use)

The CLI is `bw` (`@bitwarden/cli`). Credentials live in `~/.config/bw/agent.env` (chmod 600). The agent user `phi-0-agent` is read-only on `Homelab Secrets` — `bw edit` and `bw create` will be rejected by the server. That's intentional.

### Standard preamble (puts you in a synced/unlocked state)

```bash
source ~/.config/bw/agent.env
bw login --check >/dev/null 2>&1 || bw login --apikey >/dev/null
export BW_SESSION="$(bw unlock --passwordenv BW_PASSWORD --raw)"
bw sync >/dev/null
```

`bw login` and `bw unlock` are separate steps. Login authenticates to the server; unlock derives the vault encryption key from the master password. You need both to read items.

### Get the Telegram bot token

```bash
bw get item telegram_clawphi \
  | jq -r '.fields[] | select(.name=="token") | .value'
```

### Get the chat id

```bash
bw get item telegram_clawphi \
  | jq -r '.fields[] | select(.name=="chat_id") | .value'
```

### Get both at once (avoid two roundtrips)

```bash
ITEM=$(bw get item telegram_clawphi)
TOKEN=$(jq -r '.fields[] | select(.name=="token") | .value' <<<"$ITEM")
CHAT=$(jq -r '.fields[] | select(.name=="chat_id") | .value' <<<"$ITEM")
```

### Find/list items

```bash
bw list items --search telegram        # search by name substring
bw list items                          # everything the agent can see
bw get item <id-or-name>               # full JSON for one item
```

### Reading a Login item's password / username

If a future item stores the secret in the password field instead of a custom field:

```bash
bw get password <item-name>            # returns the password string
bw get username <item-name>            # returns the username string
```

## Apprise reference (homelab notification gateway)

Service: `https://apprise.services.phitrine.com` (Docker container at `~/docker/apprise/`, container port 8000).

### Send a message via the configured `telegram` key

```bash
curl -fsS -X POST "https://apprise.services.phitrine.com/notify/telegram" \
  --data-urlencode "body=hello"
```

(Or just use `send_telegram_message.sh` — same thing with friendlier args.)

### Configure / update a notification key

```bash
curl -fsS -X POST "https://apprise.services.phitrine.com/add/telegram" \
  --data-urlencode "urls=tgram://<bot_token>/<chat_id>"
```

In practice, never do this by hand — `scripts/apprise/refresh_configs.sh` does it from Bitwarden.

### Adding a new channel (e.g. discord)

1. Store credentials in Bitwarden under a clear item name (e.g. `discord_homelab_webhook`).
2. Extend `scripts/apprise/refresh_configs.sh` with another section that builds the [Apprise URL for that service](https://github.com/caronc/apprise/wiki) and POSTs to `/add/<key>`.
3. Send via `APPRISE_KEY=<key> ./send_telegram_message.sh "..."` — or rename the sender to `send_apprise_message.sh` if you'd rather have a generic name.

## For other agents

If you find a hand-edited secret in `telegram.env` (or any env file in this folder), assume it's stale. Always:

1. Treat Bitwarden as authoritative.
2. Regenerate via the appropriate refresh script.
3. Don't paste rotated values into the env file directly — that drifts the cache from the source.

The current sender script (`send_telegram_message.sh`) goes through Apprise and does **not** require `telegram.env` to be present. Only update `telegram.env` if you find a legacy consumer that reads it.
